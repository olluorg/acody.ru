Почему данные временных рядов сжимаются заметно лучше обычных?

MiddleБазы временных рядов
Ещё спрашивают так:
  • Как сжимаются временные ряды?
Коротко

Метки времени идут с регулярным шагом, значения меняются плавно — хранят разности (delta-of-delta для времени, XOR соседних значений для чисел), которые занимают считаные биты.

  • Схема Gorilla (Facebook): ~1,4 байта на точку вместо 16
  • Колоночное хранение рядов дополнительно помогает сжатию
  • Случайные значения сжимаются хуже — сжатие зависит от данных

А ещё Prometheus, VictoriaMetrics, InfluxDB используют похожие приёмы

Подробно

Если точки идут через равные промежутки, разность между соседними метками постоянна, и разность этих разностей почти всегда равна нулю — такие последовательности упаковываются исключительно плотно. Значения метрик тоже меняются плавно, поэтому вместо полного числа хранят его отличие от предыдущего. На реальных данных это даёт сжатие в разы по сравнению с обычным хранением, что критично при миллионах точек в секунду. Важно не путать это со снижением точности: сжатие здесь без потерь, а вот прореживание старых данных — отдельный осознанный приём для экономии места на длинном горизонте.

Что хотят услышать

  • Почему ряды хорошо сжимаются.
  • Дельта-кодирование и XOR для чисел с плавающей точкой.

Частые ошибки

  • Путать сжатие без потерь с прореживанием данных.
  • Хранить метрики в общей реляционной таблице и удивляться объёму.
