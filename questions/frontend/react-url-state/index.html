Какое состояние стоит хранить в URL и как защищать маршруты?

MiddleАрхитектура фронтенда
Ещё спрашивают так:
  • Зачем хранить фильтры в URL?
  • Как сделать приватные маршруты?
Коротко

В URL хранят то, что должно переживать перезагрузку, делиться ссылкой и работать с кнопкой «назад»: фильтры, сортировку, страницу, открытую вкладку, поисковый запрос. URL становится источником истины — компонент читает параметры, а меняет их через навигацию. Защищённые маршруты: родительский маршрут или loader проверяет авторизацию и перенаправляет на вход с параметром возврата; настоящая проверка прав — всегда на сервере, на клиенте — только удобство.

  • Значения из URL валидировать (Zod) и иметь значения по умолчанию
  • Частые изменения (ввод поиска) — с debounce и replace, чтобы не засорять историю
  • Временное состояние интерфейса (открыт ли выпадающий список) в URL не нужно

А ещё Скрытая кнопка не защищает данные — защищает API

Подробно

function RequireAuth() {
  const user = useUser();
  const loc = useLocation();
  if (!user) return <Navigate to={`/login?next=${encodeURIComponent(loc.pathname)}`} replace />;
  return <Outlet />;
}

Что хотят услышать

  • Что хранить в URL и почему.
  • Валидация и replace.
  • Защищённые маршруты и проверка на сервере.

Показать варианты и ответ
  • ✓Фильтры, сортировку и страницу хранить в URL ради ссылок, перезагрузки и «назад»; защищённые маршруты перенаправляют на вход, а права проверяет сервер
  • ✗Скрытие маршрута на клиенте надёжно защищает данные
  • ✗В URL стоит хранить всё состояние интерфейса, включая открытые подсказки
  • ✗Значения из URL можно использовать без проверки
