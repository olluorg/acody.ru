Как устроить сборку и выкатку фронтенда?

MiddleВыкатка и эксплуатация
Ещё спрашивают так:
  • Как кэшировать статические файлы фронтенда после деплоя?
  • Что такое preview-окружения?
Коротко

Пайплайн: установка по lock-файлу → линтер и типы → тесты → сборка → проверки размера → preview-окружение на каждый PR → выкатка. Статика с хешами в именах кэшируется надолго на CDN, а index.html — коротко или с проверкой, чтобы пользователи получали новую версию. Переменные окружения сборки попадают в бандл — секретам там не место.

  • Preview-окружения: дизайнер и продакт смотрят изменения до слияния
  • Старые файлы держать после выкатки — открытые вкладки ещё загружают старые чанки
  • Откат — переключение на предыдущую сборку, а не пересборка

А ещё Для SSR-приложений выкатка — как у бэкенда: контейнеры, rolling update, совместимость с API

Подробно

Кэширование:

файлзаголовок
assets/app.4f2a9c.jsCache-Control: public, max-age=31536000, immutable
index.htmlCache-Control: no-cache

Ошибка загрузки чанка после выкатки: вкладка с прошлой версией запрашивает удалённый файл. Решения — хранить прошлые сборки, перезагрузка при ошибке загрузки чанка.

Конфигурация по окружениям: одна сборка, конфиг загружается в рантайме — тот же артефакт идёт на стейдж и в прод.

Что хотят услышать

  • Этапы пайплайна и preview.
  • Стратегия кэширования статики.
  • Секреты, откат и ошибки загрузки чанков.
