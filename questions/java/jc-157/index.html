Как получить LRU-кэш на базе LinkedHashMap?

MiddleКоллекции
Ещё спрашивают так:
  • Нужен LRU-кэш на 1000 записей. Как сделать его на LinkedHashMap и за счёт чего это работает?
Коротко

new LinkedHashMap<>(cap, 0.75f, true) (accessOrder) + переопределённый removeEldestEntry, возвращающий size() > max. Get переносит запись в конец, самая давно неиспользуемая — в голове и вытесняется.

  • Без accessOrder получится FIFO, а не LRU
  • Не потокобезопасно — для многих потоков Caffeine
  • Всё за O(1)

А ещё Caffeine (W-TinyLFU) обычно даёт больше попаданий, чем LRU

Подробно

Нужны обе части. Флаг accessOrder переводит внутренний список из порядка вставки в порядок обращения: каждый get перемещает запись в конец, поэтому в голове списка всегда самая давно не используемая. Метод removeEldestEntry вызывается после вставки и по умолчанию возвращает false — пока его не переопределить, никакого вытеснения не будет. Ограничения, которые стоит назвать: реализация не потокобезопасна, а вытеснение происходит только при добавлении новой записи, поэтому карта, в которую перестали писать, не сжимается. Для конкурентного кэша с TTL берут специализированную библиотеку.

Пример

class Lru<K, V> extends LinkedHashMap<K, V> {
    private final int max;
    Lru(int max) { super(16, 0.75f, true); this.max = max; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) { return size() > max; }
}

Что хотят услышать

  • accessOrder и removeEldestEntry.
  • Почему работает и ограничения.

Частые ошибки

  • Задать accessOrder и забыть про removeEldestEntry.
  • Использовать такой кэш из нескольких потоков без синхронизации.
