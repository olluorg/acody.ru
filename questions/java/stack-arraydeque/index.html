Почему стек реализуют через ArrayDeque, а не java.util.Stack?

MiddleКоллекции
Ещё спрашивают так:
  • Чем плох java.util.Stack?
  • Почему для стека и очереди рекомендуют ArrayDeque?
  • Почему для стека и очереди рекомендуют ArrayDeque, а не Stack и LinkedList?
Коротко

Стек и очередь в одном потоке — ArrayDeque (кольцевой массив, O(1) по краям, данные подряд). Stack наследует Vector: synchronized на каждой операции и доступ по индексу в середину — нарушает абстракцию стека.

  • push/pop/peek для стека, offer/poll/peek для очереди
  • LinkedList тоже Deque, но платит узлом на элемент и промахами кэша
  • ArrayDeque не допускает null

А ещё Потокобезопасные — ConcurrentLinkedDeque, LinkedBlockingDeque

Подробно

java.util.Stack — класс Java 1.0, наследник Vector. Каждая операция синхронизирована (бесполезная цена для локального стека), и от Vector унаследованы get(i), add(i, x), remove(i) — можно залезть в середину стека. Документация сама рекомендует Deque.

ArrayDeque — кольцевой буфер на массиве с указателями головы и хвоста. Добавление и снятие с обоих концов — амортизированно O(1), элементы лежат подряд (хорошо для кэша), нет объекта-узла на элемент. Растёт удвоением.

Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); stack.push(2); stack.pop();   // 2
Deque<Task> queue = new ArrayDeque<>();
queue.offer(t1); queue.offer(t2); queue.poll();   // t1

LinkedList как очередь — медленнее ArrayDeque: узел на каждый элемент, промахи кэша, нагрузка на GC.

Многопоточно — ConcurrentLinkedDeque (без блокировок), LinkedBlockingDeque и ArrayBlockingQueue (с ожиданием).

Показать варианты и ответ
  • ✓ArrayDeque (push/pop/peek) — массив с O(1) и хорошим кэшем; Stack наследует Vector и синхронизирован на каждой операции — медленно и не нужно для локального стека
  • ✗Stack удалён из JDK, ArrayDeque — единственный вариант
  • ✗Stack хранит элементы в связном списке, поэтому медленнее
  • ✗ArrayDeque потокобезопасен, а Stack — нет
