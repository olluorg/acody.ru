Какое правило связывает equals() и hashCode()?

MiddleРавенство, equals и hashCode
Ещё спрашивают так:
  • Почему при переопределении equals обязательно переопределять и hashCode?
  • Почему в Java при переопределении equals обязательно переопределять и hashCode?
Коротко

Равные по equals объекты обязаны иметь равный hashCode; обратное не требуется — коллизии нормальны. Иначе HashMap и HashSet ищут в другой корзине и не находят равный объект: до вызова equals дело не доходит.

  • Переопределили equals без hashCode — дубликаты в HashSet, «пропавшие» ключи
  • Считать hashCode по тем же полям, что equals: Objects.hash
  • Изменяемые поля в hashCode ключа — объект потеряется после изменения

А ещё Record и Lombok @EqualsAndHashCode генерируют согласованную пару

Подробно

Как HashMap ищет ключ: вычисляет hashCode, по нему выбирает корзину, и только внутри неё сравнивает кандидатов через equals.

class Point {
    final int x, y;
    @Override public boolean equals(Object o) {
        return o instanceof Point p && x == p.x && y == p.y;
    }
    // hashCode не переопределён
}
Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2));   // скорее всего false

hashCode по умолчанию — от идентичности объекта, у двух равных точек разные хеши → разные корзины → equals не вызывается.

Контракт hashCode:

  • равные по equals — равные hashCode (обязательно);
  • неравные могут совпадать (коллизия), но чем реже — тем быстрее таблица;
  • значение стабильно, пока не меняются поля, участвующие в equals.

Правильно: Objects.hash(x, y) или вручную 31 * x + y; те же поля, что в equals.

Частые ошибки

  • Переопределить equals и забыть hashCode.
  • Делать hashCode на основе изменяемого состояния ключа.
