В конвейере стоят filter и map. Почему порядок filter перед map обычно предпочтительнее обратного?

MiddleЛямбды и Stream API
Коротко

Элементы идут по конвейеру по одному: дорогое преобразование до фильтра выполняется и для отбрасываемых элементов. Чем раньше отсеять, тем меньше работы.

  • Короткое замыкание: с findFirst и limit обработка останавливается рано
  • sorted до filter сортирует лишнее — фильтровать раньше
  • Если map нужен для условия — порядок вынужденный

А ещё peek помогает увидеть порядок обработки при отладке

Подробно

Стрим не выполняет операции пофазно над всей коллекцией — каждый элемент проходит всю цепочку до конца, после чего берётся следующий. Поэтому дорогое преобразование, поставленное до фильтра, выполняется и для отбрасываемых элементов. Ленивость даёт и более сильный эффект — короткое замыкание: findFirst, anyMatch или limit прекращают обработку, не дойдя до конца источника, что позволяет работать даже с бесконечными стримами. Автоматической перестановки операций стрим не делает: порядок ровно тот, что написан, поэтому оптимизация конвейера — забота автора. Отсюда практическое правило: сначала фильтруем и ограничиваем, потом преобразуем и сортируем.

Что хотят услышать

  • Поэлементная ленивая обработка.
  • Экономия работы.

Частые ошибки

  • Ставить sorted раньше filter и сортировать лишнее.
  • Рассчитывать, что рантайм переупорядочит операции.
