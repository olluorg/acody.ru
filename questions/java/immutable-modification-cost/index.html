Как в immutable-дизайне моделируют «изменение» и снижают его цену?

MiddleООП
Коротко

«Изменение» — новый объект: методы withX возвращают копию с одним изменённым полем. Для частых правок — изменяемый Builder, отдающий неизменяемый результат, или persistent-структуры с разделением общей части.

  • Пример JDK: LocalDate.plusDays, String.replace
  • В горячем цикле withX плодит мусор
  • Record в Java пока без встроенных withers — пишут вручную или Lombok @With

А ещё StringBuilder → String — та же схема

Подробно

Цена неизменяемости — копирование при «изменении»: методы withX возвращают копию с одним изменённым полем. Для редких изменений это дёшево; для частых берут изменяемый Builder, который собирает состояние и отдаёт неизменяемый результат, или persistent-структуры. Главное — не плодить withX в горячем цикле (мусор для GC); там уместен мутабельный буфер с заморозкой на выходе.

Что хотят услышать

  • withX и копирование.
  • Builder и persistent-структуры для частых изменений.

Частые ошибки

  • Обходить final рефлексией ради «изменения».
  • Сыпать withX в горячем цикле.
