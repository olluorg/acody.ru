Почему ArrayDeque не допускает null-элементов?

MiddleКоллекции
Коротко

null зарезервирован как сигнал «элемента нет»: poll и peek возвращают null для пустой очереди. Если бы null хранился, ответ стал бы неоднозначным.

  • Методы Queue: add/remove/element бросают исключения, offer/poll/peek возвращают специальные значения
  • То же правило в большинстве реализаций Queue и в ConcurrentHashMap
  • LinkedList null допускает — историческая непоследовательность

А ещё Нужен «пустой» элемент — Optional или объект-заглушка

Подробно

Интерфейс Queue предлагает две группы методов: бросающие исключение (add, remove, element) и возвращающие специальное значение (offer, poll, peek). Вторая группа использует null как признак пустоты, поэтому хранение null сделало бы возврат двусмысленным. По той же причине null запрещён в реализациях BlockingQueue и в ConcurrentHashMap — там невозможно отличить «значение отсутствует» от «значение равно null» при конкурентном доступе. А вот ArrayList, HashMap и HashSet null спокойно допускают, так что обобщать запрет на всю библиотеку нельзя: правило зависит от контракта конкретного интерфейса.

Что хотят услышать

  • Причина запрета.
  • Две группы методов Queue.

Частые ошибки

  • Считать, что запрет на null действует во всех коллекциях.
  • Забывать про ту же причину запрета в ConcurrentHashMap.
