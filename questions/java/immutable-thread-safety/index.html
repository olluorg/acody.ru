Почему про immutable-объект говорят «потокобезопасен без синхронизации»?

MiddleООП
Коротко

Модель памяти гарантирует: если все поля final и this не утёк из конструктора, любой поток, получивший ссылку на готовый объект, увидит поля проинициализированными — без синхронизации. Состояние не меняется, значит гонок нет.

  • Гарантия final-полей (freeze) действует даже при публикации через гонку
  • Без final объект «эффективно неизменяем» требует безопасной публикации
  • Изменяемые элементы внутри ломают гарантию

А ещё Утечка this: регистрация слушателя или запуск потока в конструкторе

Подробно

Модель памяти Java гарантирует: у объекта со ВСЕМИ полями final, чья ссылка this не «утекла» из конструктора, любой поток, получивший ссылку на готовый объект, увидит его поля корректно проинициализированными — без блокировок. Это и делает «immutable ⇒ потокобезопасен». Подробный механизм — в уроке про JMM.

Что хотят услышать

  • Гарантия final-полей.
  • Условие неутечки this.

Частые ошибки

  • Думать, что JVM сама синхронизирует immutable.
  • Публиковать this из конструктора (ломает гарантию).

Показать варианты и ответ
  • ✓Если все поля final и ссылка this не утекла из конструктора, объект безопасно публикуется (final field freeze): другой поток видит поля корректно установленными без синхронизации
  • ✗JVM автоматически синхронизирует доступ ко всем immutable-объектам
  • ✗Неизменяемые объекты всегда лежат в ThreadLocal, поэтому их не видят другие потоки
  • ✗Любое чтение объекта в Java и так атомарно и сразу видимо всем потокам
