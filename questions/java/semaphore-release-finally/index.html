Вопросы / Java / В коде вызывается semaphore.acquire(), затем работа с ресурсом, затем semaphore.release() в конце метода. Что здесь опасно?

В коде вызывается semaphore.acquire(), затем работа с ресурсом, затем semaphore.release() в конце метода. Что здесь опасно?

MiddleМногопоточность
Коротко

release не в finally: исключение навсегда съедает разрешение. С каждым сбоем параллелизм падает на единицу, пока система не встанет без единой записи в логе.

  • acquire — до try, release — в finally
  • Если acquire прерван, release вызывать нельзя — разрешение не было получено
  • Тот же принцип, что lock/unlock

А ещё Метрика доступных разрешений помогает поймать утечку

Подробно

Утечка разрешений — коварная ошибка: система работает, но с каждым исключением параллелизм падает на единицу, и в какой-то момент всё встаёт намертво без единой записи в логе о причине. Тот же принцип, что и с блокировками: захват — перед try, освобождение — в finally. Дополнительно стоит помнить про acquire с таймаутом (tryAcquire), чтобы не ждать разрешения бесконечно, и про то, что acquire бросает InterruptedException, а acquireUninterruptibly — нет.

Что хотят услышать

  • Утечка разрешений и последствия.
  • Правильная идиома.

Частые ошибки

  • Ставить acquire внутрь try — тогда finally освободит незанятое разрешение.
  • Ждать разрешение без таймаута там, где важна отзывчивость.

Показать варианты и ответ
  • ✓release не в finally: при исключении разрешение не вернётся, и пул разрешений постепенно исчерпается
  • ✗acquire нужно вызывать только из главного потока
  • ✗Semaphore нельзя использовать без явного ReentrantLock
  • ✗Ничего опасного: семафор сам возвращает разрешение при выходе из метода
