Метод помечен @Async, и внутри него SecurityContextHolder.getContext().getAuthentication() возвращает null. Почему?

MiddleSpring Security
Ещё спрашивают так:
  • Как передать пользователя в @Async-метод?
Коротко

SecurityContext хранится в ThreadLocal потока запроса и в асинхронный поток сам не переезжает. Решение — DelegatingSecurityContextAsyncTaskExecutor (или TaskDecorator), который копирует контекст.

  • То же для MDC с trace id — TaskDecorator
  • Режим MODE_INHERITABLETHREADLOCAL не подходит для пулов — потоки переиспользуются
  • Виртуальные потоки не меняют проблему

А ещё Context Propagation (Micrometer) переносит контекст автоматически

Подробно

Стратегия хранения по умолчанию — MODE_THREADLOCAL, поэтому любой переход в другой поток теряет контекст: это касается @Async, задач в собственном пуле и реактивных цепочек. Варианты решения: включить MODE_INHERITABLETHREADLOCAL, что работает для потоков, созданных напрямую, но бесполезно для пула, где потоки существовали заранее; либо, что правильнее, обернуть исполнитель в DelegatingSecurityContextExecutor или DelegatingSecurityContextAsyncTaskExecutor, который явно переносит контекст в задачу. В WebFlux механизм другой — контекст живёт в Reactor Context, а не в ThreadLocal. И совсем простой вариант: передать нужные данные о пользователе параметрами метода, не полагаясь на неявное состояние.

Что хотят услышать

  • Причина: ThreadLocal.
  • Правильное решение с executor'ом.
  • Почему не inheritable для пулов.

Частые ошибки

  • Рассчитывать, что MODE_INHERITABLETHREADLOCAL решит проблему для пула потоков.
  • Полагаться на SecurityContextHolder внутри реактивных цепочек.
