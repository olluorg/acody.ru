Когда Spring создаёт JDK dynamic proxy, а когда CGLIB-прокси?

MiddleAOP и проксиSpringSpring Boot
Ещё спрашивают так:
  • Почему Spring Boot использует CGLIB-прокси?
Коротко

JDK dynamic proxy — реализует интерфейсы бина, перехватывает только методы интерфейсов. CGLIB — подкласс бина, работает без интерфейсов. Spring Boot по умолчанию включает CGLIB (proxyTargetClass=true).

  • С JDK-прокси бин нельзя внедрить по типу класса — только по интерфейсу
  • CGLIB не перехватывает final-методы и не работает с final-классами
  • Начиная с Spring 4, конструктор вызывается один раз (Objenesis)

А ещё Kotlin-классы final по умолчанию — нужен плагин kotlin-spring

Подробно

JDK-прокси реализует те же интерфейсы, что и целевой бин, поэтому внедрять такой бин можно только по интерфейсу — попытка внедрить по конкретному классу даст ошибку приведения типа. Именно из-за этой неприятности Spring Boot по умолчанию включает proxyTargetClass и использует CGLIB, который создаёт подкласс и потому совместим с обоими вариантами внедрения. Цена CGLIB — невозможность проксировать final-классы и final-методы, а также то, что конструктор целевого класса вызывается дважды в старых версиях. Знание, что умолчание в Boot отличается от умолчания в чистом Spring Framework, ценится на собеседовании.

Что хотят услышать

  • Ограничения.

Частые ошибки

  • Считать, что при наличии интерфейса всегда будет JDK-прокси — в Spring Boot это не так.
  • Делать класс с @Transactional final.
