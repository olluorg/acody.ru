Что такое service discovery и где здесь Eureka?

MiddleSpring Cloud
Ещё спрашивают так:
  • Как сервисы находят друг друга в микросервисах?
Коротко

Service discovery — реестр живых экземпляров сервисов: сервис регистрируется при старте, клиенты находят адреса по имени. Eureka — реестр Netflix в Spring Cloud; в Kubernetes discovery встроен через Service и DNS.

  • Клиентский поиск: клиент получает список и сам балансирует (Spring Cloud LoadBalancer)
  • Серверный: запрос идёт на стабильное имя, балансирует инфраструктура (Kubernetes Service)
  • Регистрация с heartbeat — мёртвые экземпляры выпадают

А ещё В Kubernetes Eureka обычно не нужна

Подробно

Проблема: экземпляры сервисов появляются и исчезают (автомасштабирование, выкатки, падения), адреса меняются. Захардкоженные адреса не работают.

Реестр:

  • сервис при старте регистрируется (имя, адрес, порт, метаданные) и периодически шлёт heartbeat;
  • пропал heartbeat — запись удаляется;
  • клиенты запрашивают список экземпляров по имени.

Два подхода:

  • клиентский (Eureka + Spring Cloud LoadBalancer): клиент получает список экземпляров и сам выбирает, куда слать (lb://orders в WebClient/RestClient с @LoadBalanced). Гибко, но логика в каждом клиенте;
  • серверный (Kubernetes Service, Consul + прокси, облачные балансировщики): клиент обращается к стабильному имени orders, DNS и kube-proxy или service mesh распределяют запросы. Клиент проще.

Eureka — AP-реестр: при сетевых проблемах предпочитает отдавать возможно устаревший список, чем ничего (self-preservation mode). Альтернативы — Consul, ZooKeeper, etcd.

Kubernetes: Service с селектором подов, Endpoints обновляются по readiness-пробам, имя резолвится через DNS. Отдельный реестр не нужен; Spring Cloud Kubernetes умеет читать сервисы из API при необходимости.

Что хотят услышать

  • Зачем нужен discovery.
  • Регистрация, heartbeat, поиск по имени.
  • Клиентский и серверный подходы.
  • Eureka и Kubernetes.

Частые ошибки

  • Ставить Eureka в Kubernetes «по привычке».
