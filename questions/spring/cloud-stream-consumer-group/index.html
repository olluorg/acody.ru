Что произойдёт, если у двух экземпляров сервиса в Spring Cloud Stream не задать одинаковую consumer group для входящего binding?

MiddleSpring Cloud StreamSpring Cloud
Ещё спрашивают так:
  • Почему сообщение обработалось на всех экземплярах?
Коротко

Без общей группы каждый экземпляр получает анонимную группу и становится самостоятельным подписчиком: сообщение обработается столько раз, сколько экземпляров.

  • spring.cloud.stream.bindings.<name>-in-0.group=billing — экземпляры конкурируют
  • Анонимная группа в Kafka ещё и начинает с latest — пропуск сообщений при перезапуске
  • Разные сервисы — разные группы (pub/sub)

А ещё Анонимные группы подходят только для «живых» уведомлений

Подробно

Consumer group реализует семантику конкурирующих потребителей: внутри одной группы сообщение достаётся ровно одному участнику, а разные группы получают собственную копию — это и есть разница между распределением нагрузки и широковещательной рассылкой. При отсутствии явной группы Spring Cloud Stream создаёт анонимную и, как правило, недолговечную подписку, поэтому при масштабировании появляются дубли, а при перезапуске теряются сообщения, пришедшие в простое. Практическое правило: для любого потребителя в production группа задаётся явно, а широковещательная модель выбирается сознательно, когда каждому экземпляру действительно нужна своя копия — например, для инвалидации локального кэша.

Что хотят услышать

  • Поведение без группы.
  • Как задать группу и что это даёт.

Частые ошибки

  • Полагаться на умолчание и обнаружить дубли только после масштабирования.
  • Использовать анонимную группу там, где сообщения нельзя терять.
