Юнит-тесты и тесты компонентов

Основа с Junior

Vitest и Testing Library — проверять поведение, а не реализацию.

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("добавляет товар в корзину", async () => {
  render(<Product id={1} />);
  await userEvent.click(screen.getByRole("button", { name: "В корзину" }));
  expect(screen.getByText("В корзине: 1")).toBeInTheDocument();
});

Что важно знать

  • Testing Library ищет элементы так, как их видит пользователь: по роли, подписи, тексту. Тест не ломается при рефакторинге внутренностей.
  • Не проверять внутреннее состояние и количество рендеров — только видимое поведение.
  • Сетевые запросы подменять на уровне сети (MSW), а не мокать fetch в каждом тесте.
  • Таймеры — фейковые (vi.useFakeTimers), асинхронность — findBy… и waitFor.
  • Покрытие кода — ориентир, а не цель.

Критерии освоения

Junior ≈ 6 ч

  • Пишет юнит-тесты на Vitest для чистых функций
  • Пишет тест компонента через Testing Library, находя элементы по роли и подписи

Практика. Покрыть тестами утилиты и 3 компонента учебного проекта.

Middle ≈ 8 ч

  • Подменяет сеть через MSW и тестирует асинхронное поведение
  • Покрывает тестами ключевые сценарии компонентов, а не детали реализации

Практика. Написать тесты формы оформления заказа с подменой API через MSW — успех, ошибка сервера, валидация.
